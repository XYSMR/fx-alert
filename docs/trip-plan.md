# 出國換匯計畫：設計、規則、測試與維護

使用者看的說明在 [README〈出國換匯計畫〉](../README.md#出國換匯計畫)。這份文件給開發和維護用。

## 目的與原則

一般的匯率 App 要使用者自己設定目標價，但大多數人不知道該設多少，也沒考慮出國日期。
出國換匯計畫改成輸入**出發日**和**需要的外幣金額**，系統依「近 30 天的價格」和「距離出發的天數」決定什麼時候寄提醒。

- **不提供投資建議**：信件和網頁只寫事實（現在的價格在近 30 天第幾低、距離出發還有幾天、之後哪天寄信），
  不預估匯率會漲會跌，也不建議什麼時候該換。每封信、網頁都附「僅供參考，不保證未來匯率走勢」。
  `tests/test_trip_mail.py`、`site/tests/trips.test.js` 會檢查不出現「建議、應該、推薦、划算、預測、投資、時機……」等字。
- **不用 LLM 推薦目標價**：和上一點衝突，結果也難以測試。
- **和到價提醒並存**：共用帳號、通知時段、每日寄信上限、退訂連結。

## 資料流

```
兆豐牌告（每 30 分鐘）──► state 分支 history/ ──┐
seed/mega_daily_close.csv（一年份，一次性回補）──┴► daily.py：每個營業日 16:00–16:10 的最後一份 = 收盤價
                                                        │
seed/tw_bank_calendar.csv ──► bizdays.py：營業日        │
                                   │                    ▼
使用者（網頁 trips.js）──► Supabase trips / trip_exchanges ──► view active_trips
                                   │                    │
                                   ▼                    ▼
                         trip_rules.schedule / decide（純函式）
                                   │
          main._check_trips ──► trip_mail.py ──► Gmail ──► trip_notifications（寄過的紀錄）
```

網頁用 `data.json` 的 `bank_calendar` 和每個幣別的 `recent`（近 30 天統計），照同樣的規則顯示提醒日期和第幾低。

## 提醒規則（`src/fx_alert/trip_rules.py`）

D = 出發日。下面的日期都會調整成**銀行營業日**（現鈔只能在營業日換）：

| 階段 | 日期 | 寄什麼 |
|---|---|---|
| 遠期 | 建立 ～ 接近開始前 | 相對便宜：比現價低的收盤價天數 ≤ 近 30 天營業日的 **20%**（例如 20 天裡第 1～5 低）；同一趟 7 天最多 1 封 |
| 接近（`near_on`） | D-21 當天或之前最近的營業日 | 第一天寄「可以考慮分批換」1 封（不看價格）；之後 ≤ **40%**（20 天裡第 1～9 低）才寄，5 天最多 1 封 |
| 最後（`final_on`） | D-7 當天或之前最近的營業日，但最晚是出發前倒數第 3 個營業日 | 「最後換匯提醒」1 封，不看價格 |
| 出發前（`last_call`） | 出發前**倒數第 2 個**營業日 | 「出發前提醒」1 封，不看價格；最後 1 個營業日（`spare`）留著備用 |

- **週末、連假**：21 天、7 天落在非營業日時往前移（提早，不延後）。
  - 1/17（週日）出發 → 接近 12/24（12/27 週日、12/25 假日）、最後 1/8（週五）、出發前 1/14、備用 1/15。
  - 2027-02-11 出發（2/4～2/10 春節）→ 最後 2/1、出發前 2/2、備用 2/3。「最晚倒數第 3 個營業日」就是為了這種情況，
    避免最後提醒和出發前提醒擠在同一天。
- **只在營業日寄、一天最多 1 封、剩餘 0（換完）就停。**
- **固定提醒沒寄到**（例如那天沒檢查到）：下一個營業日補寄，但不會在下一個階段開始後才補。
- **建立日**（台灣時間的日期）：
  - 分批、最後：提醒日**早於**建立日才不寄；**提醒日當天建立，當天會寄**。
    例：11/24 出發（最後提醒 11/17），11/17 建立 → 當天寄；11/18 建立 → 不寄。
  - 出發前：要在提醒日**之前**建立才寄（當天建立不寄，因為隔天就是最後一個營業日）。
  - 價格提醒：沒有建立日的限制。建立時在遠期或接近階段，價格符合條件的話建立當天就可能寄；最後階段不寄價格提醒。
- **相對便宜的資料不足**：近 30 天（日曆天）少於 15 個營業日的收盤價時不判斷（`daily.MIN_CLOSES`）。
- **百分比的算法**：`recent.lower / recent.days`，`lower` = 近 30 天的收盤價裡**比現價低**的天數（一樣的不算），
  「第幾低」= `lower + 1`。

### 模擬（`python scripts/simulate_trip_rules.py`）

用兆豐一年份的收盤價，出發日 2026-03-02～11-16 每個營業日各一趟、60 天前建立、都沒換：

| 幣別 | 每趟平均 | 最少～最多 | 其中「相對便宜」（遠期＋接近） |
|---|---|---|---|
| JPY | 6.9 封 | 4～9 | 3.9 |
| KRW | 6.4 封 | 3～10 | 3.4 |
| USD | 6.1 封 | 3～9 | 3.1 |
| EUR | 7.0 封 | 4～11 | 4.0 |

固定的 3 封每趟都有；60 天大約一週 1 封。**改規則時要重跑模擬，並更新這張表和 README。**

## 資料表與權限（`supabase/migrations/20261116195500_trips.sql`）

| 表／view | 內容 | 使用者（authenticated） | 排程（service_role） |
|---|---|---|---|
| `trips` | 幣別、出發日、外幣金額、名稱 | 讀、新增、刪自己的；只能改金額和名稱 | 全部 |
| `trip_exchanges` | 已經換了多少（金額、匯率可不填、日期） | 讀、新增、改、刪自己的 | 全部 |
| `trip_notifications` | 寄過的提醒（種類、日期、當時價格、第幾低、距離出發天數、剩餘金額） | 只能讀自己的 | 新增 |
| `trip_progress`（view，security_invoker） | 已換、剩餘、筆數、最近一封提醒 | 只看得到自己的 | 讀 |
| `active_trips`（view） | 還沒出發、還沒換完、Email 開著的旅程＋email、通知時段、寄過的提醒 | — | 讀 |

資料庫本身擋住的事（不靠網頁）：
- 出發日：明天～一年內；建立後出發日、幣別不能改（提醒日期從出發日算，要改就刪掉重建）
- 每人最多 5 趟「還沒出發」的旅程（同時新增會排隊）；每趟最多 50 筆換匯紀錄
- 換匯紀錄只能掛在自己的旅程（複合外鍵 `(trip_id, user_id)`）
- 同一趟一天最多一封提醒；`near_start`、`final`、`last_call` 每趟只能一次（unique）
- 刪旅程、刪帳號 → 換匯紀錄和提醒紀錄一起刪

測試：`tests/db/test_trips.py`。

## 網頁（`site/trips.js`）

登入後出現「出國換匯計畫」區塊：建立旅程（含提醒日期預覽）、旅程進度、記錄／刪除換匯、修改金額和名稱、刪除旅程。

- 上半部是純函式（`schedule`、`previewSteps`、`progress`、`rankText`……），`site/tests/trips.test.js` 測。
- 提醒日期在網頁上用 `data.json` 的 `bank_calendar` 算。`tests/fixtures/trip_schedules.json`
  （`python scripts/make_trip_fixture.py` 產生）是 Python 算出的 2026-11-17～2027-12-31 每天出發的提醒日期：
  Python 測試確認檔案和程式一致，JS 測試逐日比對，兩邊不會算出不一樣的日期。
- 整個檔案包在自己的函式範圍：網頁的 script 共用全域，`app.js` 也有 `parseAmount` 這種名字，不包起來會互相覆蓋
  （#30 的教訓；測試確認全域只多了 `FxTrips`）。

## 寄信（`main._check_trips`、`src/fx_alert/trip_mail.py`）

每次 `check --mode multi` 在到價提醒之後，對 `active_trips` 的每趟旅程呼叫 `decide()`：

- 「相對便宜」只在**今天已經有新牌告**時判斷：早上 8 點時牌告還是前一天的，不能拿來說「現在」；
  颱風停班沒有牌告的日子也不會寄價格提醒。三封固定提醒不看價格。
- 不在使用者的通知時段：這次不判斷，時段開始後的第一次檢查再判斷（固定提醒當天會補寄）。
- 每日寄信上限：到價通知＋換匯提醒合計（只在真的有換匯提醒要寄時才查 `trip_notifications`）。
- 寄出後寫 `trip_notifications`；unique 衝突（重複或旅程剛被刪除）只記一行注意，不算錯誤。
- 公開 log 只有「旅程#N: 寄出換匯提醒 final」這種格式，不寫 email、幣別、金額、出發日、天數
  （見 README〈公開 log 的原則〉、`tests/test_log_privacy.py`）。
- 退訂連結和到價通知共用：退訂後兩種信都不寄（`active_trips` 只列 Email 開著的人）。

信件內容：原因（第幾低／距離出發幾天）、還沒換的金額和約需多少台幣、牌告時間、之後哪幾天會再寄、網站連結、免責說明、退訂連結。

## 歷史資料與營業日

- **收盤價**：2025-11-17～2026-11-16 用兆豐官方的歷史匯率一次性回補（`seed/mega_daily_close.csv`），之後用自己記錄的牌告
  （每個營業日 16:00–16:10 的最後一份）。來源、比對結果見 README〈資料來源〉和 `seed/README.md`。
- **營業日**：`seed/tw_bank_calendar.csv` = 人事行政總處「政府行政機關辦公日曆表」的假日／補假／補班＋颱風停班。
  2025-11-17～2026-11-16 和兆豐實際有牌告的 243 天逐日一致（`tests/test_bizdays.py`）。
- **找檔案**：workflow 是 `pip install .`（非 editable），`paths.repo_file()` 依序找 `FX_ALERT_ROOT` → 工作目錄 → 程式位置；
  找不到直接失敗（#31 之前會默默當成沒有資料）。CI 的 validate-config 用同樣的安裝方式確認讀得到。

## staging 驗證步驟

改了寄信相關的程式時，合併前在 staging 走一次（2026-11-17 驗證 #32 時的做法）。
每一步改資料庫之前先截圖給維護者確認。

1. **唯讀查詢**：staging 的帳號、`email_enabled`、通知時段、現在的台灣時間（要在通知時段內）
2. **建立測試旅程**（SQL Editor）：挑一個出發日，讓**今天**剛好是某個固定提醒日，而且今天建立還會寄
   （例：今天是週二 → 出發日 = 下週二，最後提醒 = 今天）。用 `decide()` 先在本機確認預期結果。
3. **staging-check，勾 send**：預期寄出 1 封、`trip_notifications` 多 1 筆、log 只有「旅程#N: 寄出換匯提醒 …」
4. **再跑一次**：預期不再寄（防重複）
5. **刪除測試旅程**：要在下一個固定提醒日（通常是出發前提醒）**之前**刪，不然會再寄一封

注意：
- 信裡的退訂連結打開後**只看頁面**；按了確認會關掉 staging 帳號的 Email 通知，之後的步驟就測不準
  （關掉的話用 SQL 把 `profiles.email_enabled` 改回 true）。
- staging-check 每次會先跑 `unsubscribe-check`，確認 `STAGING_UNSUBSCRIBE_SECRET` 和 staging Edge Function 一致。
- 每 30 分鐘自動跑的 staging-check 只讀不寫，不會寄信。

## 維護

| 時候 | 做什麼 |
|---|---|
| 每年約 6 月（人事行政總處公布隔年日曆） | 補 `seed/tw_bank_calendar.csv`、改 `bizdays.COVERED_UNTIL`、`seed/README.md` 記來源和 SHA-256、改 `scripts/make_trip_fixture.py` 的 `LAST` 後重新產生對照檔（步驟見 README〈定期維護〉） |
| 颱風停班之後 | 確認兆豐那天沒有收盤價，在日曆加 `off` 一行 |
| 改提醒規則 | 改 `trip_rules.py` 和 `site/trips.js` 的 `schedule`／`previewSteps`，重新產生對照檔、重跑模擬，更新這份文件和 README |
| 改信件或網頁用語 | 跑用語檢查的測試；不要出現預估走勢或叫人買賣的字 |

營業日曆過期時（旅程的出發日超過涵蓋範圍），排程的 log 會提醒；那些日期只用「週一到週五」判斷營業日。

## 已知限制

- 未來的颱風停班沒辦法預先知道（見上面的備用日）。
- 「近 30 天」只用兆豐一家銀行的現金賣出價；不同銀行、分行的實際價格和手續費不同。
- 價格提醒一天最多判斷出一封；牌告在兩次檢查之間短暫變便宜不會發現（和到價提醒一樣）。
- 沒有推播，只有 Email（PWA＋推播是下一階段的待辦）。
